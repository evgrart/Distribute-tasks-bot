# Telegram-бот распределения задач

> Статус: бот реализован в `TelegramBot.gs`; алгоритм проверяется файлом `TelegramBot.test.js`.

## 1. Назначение

Бот добавляется в беседу учебной группы, читает выбранный лист практики из Google Sheets и отправляет распределение в формате:

```text
Практика 6 — Артём

@student_one — задача 4
@student_two — задачи 7, 19
@student_three — задача 12

Покрыто: 24 из 30 задач
Без подходящего докладчика: 3, 11, 28, 30
```

Главная цель распределения — назначить докладчиков на наибольшее возможное количество **разных** задач. Одна задача в одном запуске назначается не более чем одному студенту, а один студент получает не более двух задач за практику.

Бот только читает таблицы и отправляет сообщение. Он не заменяет `+` на `1` и не изменяет баллы D.

## 2. Откуда берутся данные

Бот использует четыре существующие Google-таблицы:

- `ДМобщее`, лист `Общий` — ФИО, практик, Telegram и статус `Прод`;
- `ДМАртём`, лист `Практика N`;
- `ДМРами`, лист `Практика N`;
- `ДМНемат`, лист `Практика N`.

В команде указываются номер таблицы практика и номер практики:

| Номер | Таблица |
|---:|---|
| 1 | Артём |
| 2 | Рами |
| 3 | Немат |

Например, команда `/preview 1 6` означает: взять `ДМАртём`, открыть лист `Практика 6` и построить черновик распределения.

Telegram студента берётся из столбца `TG` листа `Общий` по совпадающему ФИО. Значения `username` и `@username` считаются одинаковыми; в сообщение всегда выводится `@username`.

## 3. Кто допускается к распределению

Студент рассматривается как кандидат, если одновременно выполнены условия:

1. студент есть в `Общий` и относится к выбранному практику;
2. у него не установлен `Прод = Нет`;
3. под конкретной задачей стоит именно `+`;
4. студент ещё не исчерпал лимит двух выходов за эту практику;
5. выполнено правило присутствия для выбранного практика.

Правила присутствия с учётом текущего устройства таблиц:

- **Артём и Немат** — участвуют только студенты с `Присутствие = Да`;
- **Рами** — столбца присутствия нет, поэтому учитывается только наличие `+`.

Пустое присутствие и `Нет` у Артёма и Немата означают, что студент в распределение не входит.

Апостроф перед плюсом не мешает: введённое в Google Sheets значение `'+` нормализуется ботом до `+`.

## 4. Как учитываются `+`, `1` и `-`

- `+` — студент решил задачу и может быть назначен на неё;
- `1` — задача уже была успешно рассказана этим студентом;
- `-` — штраф, задача не считается покрытой и студент не становится кандидатом на неё;
- пустая ячейка — студент не заявлял решение.

Каждая существующая `1`:

- считается одним уже использованным выходом студента на этой практике;
- помечает задачу уже покрытой, поэтому бот повторно её не назначает.

Оставшаяся вместимость студента рассчитывается так:

```text
доступно назначений = max(0, 2 − количество единиц в строке студента)
```

`-` не занимает один из двух обычных выходов. Это соответствует текущей логике D, где штраф хранится отдельно от обычного выхода.

## 5. Алгоритм распределения

### 5.1. Граф кандидатов

Бот строит двудольный граф:

- слева находятся допущенные студенты;
- справа — ещё не покрытые задачи;
- ребро `студент → задача` существует, только если в соответствующей ячейке стоит `+`.

У задачи вместимость равна `1`. У студента вместимость равна `1` или `2` в зависимости от уже имеющихся единиц.

### 5.2. Приоритеты

Оптимизация выполняется строго в следующем порядке:

1. **Максимальное покрытие.** Сначала находится распределение с максимально возможным количеством разных задач.
2. **Больше вовлечённых студентов.** При одинаковом покрытии бот старается сначала выдать по одной задаче большему числу студентов и только затем вторую задачу одному человеку.
3. **Поддержка решивших меньше.** При остальных равных предпочтение получает студент, который решил меньше задач за весь семестр. Бот суммирует его `+` и `1` на всех 15 практиках. Значения `-` в эту статистику не входят.
4. **Небольшая случайность.** Полностью равные варианты перемешиваются случайно, чтобы распределение нельзя было заранее угадать.

Таким образом, случайность никогда не уменьшает достижимое покрытие задач. Она используется только как последний критерий выбора.

### 5.3. Реализация алгоритма

Для этого подходит задача минимальной стоимости максимального потока:

```text
источник → два слота каждого студента → разрешённые задачи → сток
```

- максимальный поток отвечает за количество покрытых задач;
- стоимость второго слота не даёт без необходимости назначать две задачи одному студенту;
- небольшая стоимость, зависящая от числа решений за все 15 практик, создаёт приоритет для решивших меньше;
- случайная добавка разбирает полные ничьи.

Это даёт точное максимальное покрытие, в отличие от простого последовательного жадного выбора, который может случайно занять студента не той задачей и потерять покрытие.

## 6. Пример

Пусть отмечены плюсы:

```text
Анна:  1, 2
Борис: 2, 3
Вера:  3
```

Алгоритм рассматривает распределение целиком и найдёт, например:

```text
Анна  → 1
Борис → 2
Вера  → 3
```

Все три задачи покрыты, а работа распределена между тремя студентами.

## 7. Команды бота

Мгновенной команды `/distribute` не будет. Распределение всегда проходит через черновик и ручное подтверждение.

Доступные команды в личном диалоге с ботом:

- `/preview 1 6` — рассчитать и показать черновик для таблицы №1, практики №6;
- `/repeat` — повторно показать последнее сохранённое распределение без пересчёта;
- `/reroll` — пересчитать последнее распределение с новой случайностью;
- `/help` — показать краткую инструкцию.

Под черновиком находятся inline-кнопки:

- `✅ Опубликовать` — отправить в беседу ровно тот вариант, который показан в черновике;
- `🎲 Пересчитать` — построить другой вариант с новой случайностью, сохраняя все ограничения;
- `✖ Отменить` — удалить черновик без публикации.

Черновик показывается в личном диалоге практика с ботом. В обычной Telegram-беседе невозможно показать сообщение только одному участнику, поэтому команда `/preview`, отправленная в группу, не публикует черновик, а предлагает открыть личный диалог с ботом.

Вместо ручного ввода чисел уже доступны пошаговые inline-кнопки:

```text
Выберите практика → выберите практику 1–15 → черновик → опубликовать или пересчитать
```

Команды расчёта и кнопки публикации доступны только Telegram ID практиков, перечисленным в конфигурации. Студенты видят итоговое сообщение в беседе, но не могут создавать или подтверждать распределения.

## 8. Повторные запуски и одновременная работа

Для пары `практик + номер практики` бот сохраняет:

- выданное распределение;
- дату и время запуска;
- Telegram ID запустившего практика;
- случайное зерно;
- контрольный отпечаток прочитанных данных.

`/repeat` показывает тот же черновик. `/reroll` явно создаёт новый. Подтверждение не перечитывает таблицу и не пересчитывает алгоритм: в беседу уходит именно показанный вариант.

Бот рассчитан на один запуск в начале занятия после того, как практик отметил присутствующих и студенты расставили плюсы.

Если два практика одновременно запустят команды для разных таблиц, они не мешают друг другу. Два одновременных запуска для одной таблицы и практики защищаются блокировкой: второй запрос получает уже рассчитанный результат либо сообщение, что расчёт выполняется.

## 9. Проверки и сообщения об ошибках

Перед распределением бот проверяет:

- существует ли выбранная таблица и лист `Практика N`;
- распознаны ли колонки `ФИО`, `Присутствие`, `S` и заголовки задач;
- есть ли соответствующее ФИО в `Общий`;
- нет ли одинаковых ФИО или одинаковых Telegram у разных студентов;
- не превышен ли уже лимит двух единиц.

После распределения бот отдельно сообщает:

- задачи без единого подходящего кандидата;
- студентов без Telegram;
- студентов, исключённых из-за отсутствия;
- студентов, у которых уже два выхода;
- итоговое количество покрытых задач.

Отсутствие Telegram не исключает студента из распределения. В таком случае вместо упоминания бот выводит ФИО:

```text
Иванов Иван — задача 7 (TG не указан)
```

## 10. Реализованная архитектура

### 10.1. Общая схема

Бот работает в том же Google Apps Script-проекте, где находится `Code.gs`:

```text
Практик в Telegram
        ↓ команда /preview или нажатие кнопки
Telegram Bot API
        ↓ HTTPS webhook
Google Apps Script: doPost(e)
        ├── проверка пользователя и команды
        ├── чтение четырёх Google-таблиц
        ├── расчёт распределения
        ├── сохранение черновика
        └── отправка ответа через Telegram Bot API
```

В проект добавляется отдельный файл `TelegramBot.gs`. Существующий `Code.gs` продолжает отвечать за таблицы, баллы и синхронизацию; бот использует его объект `DM` с ID файлов, но не меняет расчёт D и CW.

### 10.2. Почему Apps Script

Apps Script одновременно выполняет роль небольшого сервера и клиента Google Sheets:

- не нужен отдельный хостинг или постоянно включённый компьютер;
- не нужен сервисный аккаунт Google;
- код выполняется от имени владельца проекта и видит все четыре таблицы;
- доступны уже используемые `LockService`, `PropertiesService` и `SpreadsheetApp`;
- развертывание выполняется как Web App с одним HTTPS-адресом.

### 10.3. Telegram webhook

После создания бота через BotFather его webhook настраивается на URL развернутого Apps Script Web App. Telegram отправляет каждую команду и нажатие inline-кнопки в функцию `doPost(e)`.

Обработчик выполняет только маршрутизацию:

1. проверяет секрет webhook;
2. проверяет Telegram ID пользователя;
3. определяет тип события: команда, подтверждение, пересчёт или отмена;
4. вызывает нужную внутреннюю функцию;
5. после обработки возвращает Telegram ответ HTTP 200; повторно доставленные `update_id` отсекаются кэшем.

Повторные доставки одного и того же Telegram `update_id` отсекаются через `CacheService`.

### 10.4. Конфигурация и секреты

В `Script Properties` хранятся:

| Ключ | Назначение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен от BotFather |
| `TELEGRAM_WEBHOOK_SECRET` | секретная часть webhook |
| `ALLOWED_USER_IDS` | Telegram ID Артёма, Рами и Немата |
| `ADMIN_USER_IDS` | необязательный список администраторов, которые могут управлять чужими черновиками |
| `TARGET_CHAT_IDS` | соответствие таблиц 1–3 нужным беседам |
| `TELEGRAM_WEB_APP_URL` | необязательный URL Web App; обычно скрипт определяет его сам |

Например, `TARGET_CHAT_IDS` может хранить JSON:

```json
{"1":"-1001111111111","2":"-1002222222222","3":"-1003333333333"}
```

Если используется одна общая беседа, во всех трёх полях указывается один chat ID. Токен и секрет никогда не записываются в Git или непосредственно в `TelegramBot.gs`.

### 10.5. Доступ к таблицам

При создании черновика бот пакетно читает:

- лист `Общий` центрального файла — ФИО, практик, TG и `Прод`;
- выбранный лист `Практика N` — присутствие, текущие `+`, `1` и `-`;
- остальные 14 листов того же практика — только ФИО и диапазон задач для подсчёта семестрового количества решений.

Данные читаются крупными прямоугольными диапазонами через `getDisplayValues()`. После чтения каждого листа алгоритм работает с массивами в памяти; отдельных запросов к каждой ячейке нет. Это сохраняет нормальную скорость даже при 15 листах по 30 студентов и 30 задач.

Если студент переводился между практиками, штатная синхронизация ДМсистемы уже переносит его отметки по ФИО. Перед использованием бота таблицы должны быть синхронизированы обычной кнопкой системы.

### 10.6. Хранение черновика

После `/preview` создаётся короткий случайный `draftId`. В `PropertiesService` сохраняются:

- владелец черновика — Telegram ID практика;
- выбранные практик и номер практики;
- готовый текст сообщения;
- структурированный список назначений;
- случайное зерно;
- время создания;
- контрольный отпечаток исходных данных.

В `callback_data` Telegram-кнопок передаётся только короткая команда и `draftId`, поскольку Telegram ограничивает размер callback-данных.

Черновик живёт ограниченное время, например два часа. Подтвердить, пересчитать или отменить его может только создавший практик либо явно указанный администратор.

### 10.7. Публикация

При нажатии `✅ Опубликовать` бот:

1. получает блокировку;
2. проверяет владельца и срок жизни черновика;
3. проверяет, что этот `draftId` ещё не публиковался;
4. отправляет сохранённый текст в chat ID выбранного практика;
5. помечает черновик опубликованным;
6. заменяет кнопки под личным сообщением на статус `Опубликовано`.

Если Telegram временно не принял сообщение, черновик остаётся неопубликованным и кнопку можно нажать повторно. Защита по `draftId` не позволит отправить одно распределение дважды.

### 10.8. Параллельные запуски и блокировки

`LockService` защищает создание и публикацию черновиков. Два практика могут одновременно работать с разными группами. Для одинаковой пары `таблица + практика` второй запуск либо получает существующий свежий черновик, либо ждёт завершения первого расчёта.

Privacy Mode у бота можно оставить включённым: обычные сообщения студентов ему не нужны. В группе он должен получать только команды и отправлять утверждённое распределение.

## 11. Пошаговый алгоритм распределения

### Шаг 1. Получение запроса

Практик в личном диалоге выбирает таблицу и номер практики. Бот проверяет диапазоны: таблица `1–3`, практика `1–15`, пользователь входит в список разрешённых.

### Шаг 2. Снимок данных

Бот одним запуском получает согласованный снимок таблиц. Последующие изменения в Google Sheets не меняют уже показанный черновик. Чтобы учесть новые плюсы или присутствие, практик нажимает `Пересчитать`.

### Шаг 3. Нормализация

Для каждого значения удаляются лишние пробелы и служебный апостроф. `'+` и `+` становятся одним состоянием. Telegram приводится к виду `@username`. ФИО используется как ключ связи между центральной таблицей и плюсовиком.

### Шаг 4. Фильтрация студентов

Из текущей практики исключаются:

- студенты с `Прод = Нет`;
- студенты другого практика;
- у Артёма и Немата — студенты без `Присутствие = Да`;
- студенты, у которых уже две единицы на этой практике.

Отсутствие TG не является причиной исключения.

### Шаг 5. Подсчёт семестрового приоритета

Для каждого оставшегося студента бот просматривает все 15 практик и считает количество ячеек со значениями `+` или `1`. Получается `semesterSolved` — сколько задач студент заявил решёнными за семестр.

Чем меньше `semesterSolved`, тем выше мягкий приоритет студента. Этот показатель никогда не может уменьшить максимальное покрытие задач.

### Шаг 6. Уже покрытые задачи и свободные слоты

Задача считается уже покрытой, если в её столбце текущей практики есть хотя бы одна `1`. Она не участвует в новом распределении.

Для каждого студента создаётся столько свободных слотов, сколько осталось до лимита двух выходов. Если единиц нет — два слота, если одна — один, если две — ноль.

### Шаг 7. Построение графа

Для каждого свободного слота добавляются рёбра только к тем непокрытым задачам, под которыми у студента стоит `+`. Задача имеет вместимость один, поэтому двух докладчиков на неё назначить нельзя.

### Шаг 8. Максимальный поток и стоимость

Сначала алгоритм отправляет максимально возможный поток — это точное максимальное количество покрытых задач. Затем среди решений такого же размера минимизируется стоимость.

Стоимость назначения:

```text
стоимость = штраф_за_второй_слот
           + semesterSolved × вес_приоритета
           + случайный_тайбрейк
```

Весовые разряды разделяются так, чтобы:

1. второй слот использовался только после возможности вовлечь другого подходящего студента;
2. разница в `semesterSolved` была важнее случайности;
3. случайность выбирала только между действительно равными вариантами.

### Шаг 9. Формирование черновика

Назначения группируются по студенту и сортируются для читаемости. Для заполненного TG выводится упоминание, иначе ФИО. Внизу указываются статистика покрытия и задачи без кандидатов.

После достижения максимального покрытия алгоритм останавливается. Дополнительные повторные назначения на уже покрытые задачи не создаются, даже если у кого-то остался второй свободный выход.

### Шаг 10. Подтверждение

Черновик отправляется только практику. `Пересчитать` повторяет шаги 2–9 с новой случайностью. `Опубликовать` отправляет сохранённый черновик в настроенную беседу без изменений.

## 12. Согласованные решения

1. Присутствие обязательно у Артёма и Немата; у Рами оно не проверяется.
2. `1` занимает один из двух выходов; `-` выход не занимает.
3. Приоритет считается по количеству решений за все 15 практик семестра.
4. Студент без TG остаётся кандидатом и выводится по ФИО.
5. Прямой публикации нет: сначала приватный черновик, затем ручное подтверждение.
6. После максимального покрытия дополнительные дубли задач не назначаются.

## 13. Файлы

- `TelegramBot.gs` — webhook, команды, чтение таблиц, алгоритм, черновики и публикация;
- `TelegramBot.test.js` — локальные тесты чистого алгоритма;
- обновлённый `Sheet/Code.gs` — добавляет подменю `DM система → Telegram-бот`.

В сам Apps Script нужно переносить только содержимое `TelegramBot.gs` и актуального `Code.gs`. Файл тестов в Apps Script добавлять не нужно.

## 14. Полная установка

### 14.1. Создание бота

1. Откройте `@BotFather` в Telegram.
2. Выполните `/newbot` и сохраните выданный токен.
3. Добавьте созданного бота в нужную беседу.
4. Privacy Mode можно оставить включённым: бот обрабатывает команды и свои кнопки, обычные сообщения ему не нужны.

### 14.2. Добавление кода

1. Откройте центральную Google-таблицу `ДМобщее`.
2. Перейдите `Расширения → Apps Script`.
3. Замените `Code.gs` актуальным файлом `Sheet/Code.gs` и сохраните свои четыре ID в объекте `DM`.
4. Нажмите `+ → Script`, создайте файл с именем `TelegramBot`.
5. Вставьте в него всё содержимое `TelegramBot/TelegramBot.gs`.
6. Сохраните проект.

Не создавайте второй `doPost` и второй `onOpen`: `doPost` находится в `TelegramBot.gs`, а общее меню — в `Code.gs`.

### 14.3. Первичные Script Properties

В Apps Script откройте `Project Settings → Script Properties` и сначала добавьте:

| Ключ | Первичное значение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен от BotFather |
| `TELEGRAM_WEBHOOK_SECRET` | случайная длинная строка без пробелов |

Секрет можно придумать самостоятельно, например 32–64 случайных латинских символа и цифры. Не публикуйте токен и секрет в GitHub.

### 14.4. Развёртывание Web App

1. Нажмите `Deploy → New deployment`.
2. Выберите тип `Web app`.
3. `Execute as` — ваш аккаунт, у которого есть доступ ко всем четырём таблицам.
4. `Who has access` — `Anyone`. Telegram обращается к webhook без Google-авторизации.
5. Нажмите `Deploy`, подтвердите разрешения и сохраните URL, заканчивающийся на `/exec`.
6. При необходимости запишите этот URL в свойство `TELEGRAM_WEB_APP_URL`. Обычно `ScriptApp.getService().getUrl()` определяет его автоматически.

После каждого изменения кода создавайте новую версию существующего deployment через `Deploy → Manage deployments → Edit → New version`. Сам адрес webhook при этом остаётся прежним.

### 14.5. Установка webhook и получение ID

1. Перезагрузите Google-таблицу, чтобы появилось подменю `DM система → Telegram-бот`.
2. Нажмите `Установить webhook` и разрешите Apps Script доступ к внешним запросам.
3. Напишите боту в личку `/id`. Он покажет ваш Telegram ID.
4. В нужной групповой беседе отправьте `/id@имя_бота`. Бот покажет ID беседы; у групп это обычно отрицательное число.
5. Повторите для всех практиков и бесед, если беседы разные.

Команда `/id` специально доступна до настройки списка практиков, но она показывает только ID отправителя и текущего чата.

### 14.6. Финальные Script Properties

Добавьте оставшиеся свойства. ID разрешается хранить JSON-массивом или строкой через запятую:

```text
ALLOWED_USER_IDS = ["111111111","222222222","333333333"]
ADMIN_USER_IDS = ["111111111"]
TARGET_CHAT_IDS = {"1":"-1001111111111","2":"-1002222222222","3":"-1003333333333"}
```

Если все три группы используют одну беседу, повторите один chat ID для ключей `1`, `2` и `3`. `ADMIN_USER_IDS` можно оставить пустым.

После заполнения нажмите `DM система → Telegram-бот → Проверить настройки`. Результат проверки также появляется в журнале выполнения Apps Script.

### 14.7. Первая проверка

1. В файле практика отметьте присутствие и расставьте тестовые `+`.
2. В личке бота выполните `/preview 1 1`.
3. Проверьте покрытие, лимит двух выходов и список назначений.
4. Нажмите `Пересчитать`, чтобы убедиться, что меняется только случайный выбор среди равных вариантов.
5. Нажмите `Опубликовать` и убедитесь, что ровно показанный черновик появился в заданной беседе.

Бот не ставит `1` автоматически. После рассказа практик по-прежнему заменяет нужный `+` на `1` в таблице.

## 15. Обновление и диагностика

- `Проверить настройки` — проверяет токен, четыре таблицы, листы и chat ID;
- `Установить webhook` — привязывает Telegram к текущему `/exec`-адресу и обновляет список команд;
- `Информация о webhook` — пишет состояние webhook и последнюю ошибку Telegram в Execution log;
- `Удалить webhook` — временно отключает получение событий;
- `/id` — показывает ID пользователя и чата;
- `/repeat` — не перечитывает таблицу, а показывает сохранённый черновик;
- `/reroll` — заново читает таблицы и строит новый вариант.

Если бот не отвечает, последовательно проверьте:

1. deployment имеет доступ `Anyone` и выполняется от имени владельца;
2. после изменения кода deployment обновлён до `New version`;
3. webhook установлен после развёртывания;
4. `TELEGRAM_BOT_TOKEN` и `TELEGRAM_WEBHOOK_SECRET` заполнены без лишних пробелов;
5. ваш ID входит в `ALLOWED_USER_IDS`;
6. ключи `1`, `2`, `3` присутствуют в `TARGET_CHAT_IDS`;
7. ID четырёх Google-таблиц заполнены в объекте `DM`.

## 16. Проверка алгоритма локально

При установленном Node.js из корня репозитория выполните:

```bash
node TelegramBot/TelegramBot.test.js
```

Тесты проверяют фиксированные пограничные сценарии и 300 случайных двудольных графов. Для каждого случайного графа максимальное покрытие бота сравнивается с точным результатом полного перебора.
